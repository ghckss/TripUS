# UI·제품 기획 변경 기록

사용자가 실제로 보는 화면과 서비스 동작의 변경 이유를 추적하는 문서다. 최신 변경을 위에 추가한다.

## 기록 기준

- **UI 변경:** 화면 구조, 컴포넌트, 문구, 상태 표시, 입력 방식, 탐색 흐름
- **기획 변경:** 사용자 정책, 기능 범위, 생성·검증 규칙, 예외 및 실패 처리
- **기록 제외:** 사용자 경험에 영향을 주지 않는 내부 리팩터링, 테스트 코드만의 변경

각 항목에는 대상, 변경 내용, 이유, 사용자 영향과 관련 커밋을 기록한다. 기존 제품 기준 자체가 달라지면 `product-plan.md` 등 관련 기준 문서도 함께 수정한다.

## 2026-11-25

### 일정 장소 사이 소요시간 표시 제거

- **대상:** 일정 편집의 장소 카드 사이 연결 영역
- **유형:** UI 및 경로 조회 범위 변경
- **변경 내용:** 장소 카드 사이의 분 단위 소요시간, 이동 수단, 계산 중 표시와 `확인 불가 · 다시 조회` 상태를 모두 제거하고 순서를 나타내는 연결선만 유지한다. 일정 편집 화면은 인접 장소별 경로 API를 호출하지 않는다.
- **이유:** Google Maps Platform이 일본 대중교통 경로를 제공하지 않아 실제 교통이 존재하는 구간도 확인 불가 또는 사용자 의도와 다른 대체 수단으로 표시될 수 있고, 국가별 공급자 없이 일관된 정확도를 보장할 수 없기 때문이다.
- **사용자 영향:** 일정에서는 장소 순서와 각 장소의 방문 시각에 집중하며, 장소 사이에서 부정확하거나 비어 있는 소요시간을 보지 않는다.

## 2026-11-24

### AI 일정 순서·저장 경쟁과 도보 제한 보정

- **대상:** AI 일정 생성, 일정 저장, 일정 편집의 구간 이동시간
- **유형:** 생성·저장·경로 조회 정책 변경
- **변경 내용:** 최종 AI 응답의 날짜별 방문을 시작 시각순으로 정렬한 뒤 position을 저장한다. 같은 여행의 비동기 생성 작업은 DB 상태를 원자적으로 선점한 작업자 하나만 실행하며, 신규 장소의 Google Place ID가 동시에 저장된 경우 이미 생성된 장소를 재사용한다. 새 일정에서 빠진 기존 AI 추천 장소는 보관함에서 삭제하지 않는다. 대중교통 조회 실패 시에는 사용자가 선택한 대체 수단만 조회하고, 추가 요청에 `도보 10분`처럼 최대 도보 시간이 있으면 이를 넘는 도보 결과를 표시하지 않는다.
- **이유:** 실제 로그에서 같은 작업이 서로 다른 Lambda 인스턴스에서 동시에 실행돼 장소 고유키 충돌이 발생했고, 뒤늦은 생성과 추천 장소 정리가 화면 스냅샷의 장소를 제거해 `PLACE_NOT_IN_TRIP` 저장 충돌을 만들 수 있었다. 또한 AI 응답 배열과 방문 시각이 역전됐고, Google 대중교통 빈 결과를 제한 없는 도보로 대체해 72~303분 구간이 노출됐다.
- **사용자 영향:** 생성 결과의 카드 순서와 방문 시각이 일치하고, 생성 직후 일정 저장이 다른 작업이나 장소 정리 때문에 충돌하지 않는다. 요청한 도보 상한을 넘는 장거리 도보는 유효 이동시간으로 보이지 않으며 조회 가능한 허용 수단이 없으면 다시 조회 가능한 `확인 불가` 상태를 유지한다.
- **관련 커밋:** 이 변경을 포함한 커밋

### 일본 이동시간의 실제 도보·차량 폴백 추가

- **대상:** 일정 편집의 장소 간 이동시간 조회·표시
- **유형:** 경로 조회 정책 및 UI 문구 변경
- **변경 내용:** Google Routes에서 대중교통 경로가 빈 결과로 반환되면 같은 장소 쌍의 실제 도보 경로를 다시 조회한다. 사용자가 자동차를 선택한 여행은 차량 경로도 이어서 조회한다. 대체 결과는 기존 분 숫자와 구분해 `도보 N분` 또는 `차량 N분`으로 표시하고, 모든 허용 경로가 없을 때만 `확인 불가 · 다시 조회`를 유지한다. 서버 응답에 실제 계산 수단과 폴백 여부를 추가하고 폴백 발생을 구조화 로그로 기록한다.
- **이유:** 배포된 Google 키와 도쿄 대표 장소로 재현한 결과 자동차·도보 경로는 반환됐지만 Routes API와 Directions API의 일본 TRANSIT 요청은 모두 정상 HTTP 응답 안에서 빈 경로를 반환했다. 앱은 이를 모든 구간의 `확인 불가`로만 표시하고 있었다.
- **사용자 영향:** 일본 등 Google 대중교통 커버리지가 없는 지역에서도 실제 계산된 이동시간을 확인할 수 있으며, 대체 수단을 라벨로 구분해 대중교통 시간으로 오인하지 않는다.
- **관련 커밋:** 이 변경을 포함한 커밋

### AI 일정의 실제 방문일 최종 검토 추가

- **대상:** AI 전체 일정 생성·날짜별 업데이트·운영정보 및 개인화 조건 검토
- **유형:** 생성·검증 정책 변경
- **변경 내용:** 첫 생성 결과를 사용자 입력과 함께 별도 최종 검토 요청의 입력으로 다시 전달한다. 최종 검토는 초안에 확정된 장소별 방문일을 기준으로 공식 시설·정부·운영 주체의 해당 연도·월 달력을 검색해 임시 휴관·공휴일 대체 휴관·계절 휴장·공사·입장 마감을 확인하고, 휴관 장소는 날짜 이동 또는 같은 선호의 실제 대안으로 수정한다. 추가 요청의 시간 범위·회피 유형·최대 도보 시간, 선택 이동 수단과 예산 성향도 다시 대조한다. 검토 요청 자체가 기술적으로 실패하면 사용 가능한 최초 초안을 유지해 새 사용자 실패를 만들지 않는다.
- **이유:** 2026년 11월 30일이 공식 달력상 휴원일인데도 신주쿠 교엔이 배치됐고, 단일 생성 요청의 웹 검색만으로는 초안에 포함된 각 장소의 실제 방문일과 이동·예산 조건을 충분히 재검토하지 못했기 때문이다.
- **사용자 영향:** 다음 생성부터 실제 방문일에 닫힌 장소와 구체적인 개인화 조건 위반이 저장되기 전에 한 번 더 수정된다. 화면 입력·응답 형식과 기존 일정은 변경하지 않는다.
- **관련 커밋:** 이 변경을 포함한 커밋

### dev 브랜치 AWS API 자동 배포

- **대상:** GitHub Actions·AWS dev API 배포 흐름
- **유형:** 개발·배포 운영 정책 변경
- **변경 내용:** `dev` 브랜치 push 시 PostgreSQL을 포함한 타입 검사·린트·테스트·빌드와 API 계약 검증을 먼저 수행하고, 성공한 커밋만 서울 리전의 TripUS dev 스택에 CDK steady 배포한다. 기존 수동 diff/deploy와 운영 단계별 배포는 유지한다.
- **이유:** 코드가 커밋·push된 뒤에도 AWS dev API가 이전 프롬프트와 서버 코드를 실행해 최신 앱과 구버전 API가 섞여 검증되던 문제를 방지하기 위해서다.
- **사용자 영향:** dev 브랜치가 업데이트되면 별도 수동 배포 없이 검증된 API가 AWS dev 환경에 반영된다. 운영 환경은 자동 배포되지 않는다.

### AI 일정에 전체 사용자 요청 전달

- **대상:** AI 일정 전체 생성·날짜별 업데이트·최근 요청 불러오기
- **유형:** 생성 입력 정책 수정
- **변경 내용:** 화면과 API에만 저장되던 동행자, 예산, 복수 이동 수단과 추가 요청사항을 여행 방식과 함께 최종 모델 입력에 전달한다. 추가 요청의 장소·투어·시간대·선호·회피 조건은 여행 경계와 실제 운영 가능성 안에서 우선 반영하고, 여러 장소를 뜻하는 투어 약칭은 웹 검색으로 실제 구성을 확인하도록 프롬프트를 보강한다. 날짜별 업데이트도 저장된 최근 요청을 동일하게 사용한다.
- **이유:** 사용자가 입력한 핵심 요청이 모델 직전 단계에서 제거되어 투어와 방문 시간대 등이 일정에서 무시되던 문제를 해결하기 위해서다.
- **사용자 영향:** 동행 구성, 비용 성향, 선택한 이동 방법과 자유 입력 요청이 실제 생성 일정에 반영된다.
- **관련 커밋:** 이 변경을 포함한 커밋

### QA 실패 복구·상태 안내 보강

- **대상:** 장소 추가, 일정 이동시간, AI 날짜 재생성, 보관 여행 상세, 여행 삭제
- **유형:** UI·오류 처리·상태 정책 수정
- **변경 내용:** 장소 저장이 완료되면 현재 검색 후보에 남은 숨은 설명 초안까지 정리해 잘못된 미저장 경고를 방지한다. 이동시간 조회 실패 구간은 `확인 불가 · 다시 조회`로 표시하고 해당 구간만 즉시 다시 요청할 수 있게 한다. 과거 여행의 이동시간은 같은 요일·시각의 다음 운행일로 보정해 조회하며, 경로 없음·공급자 실패는 원인을 구분한 구조화 로그로 남긴다. 백그라운드 AI 생성에서 무료 한도 오류 코드를 보존해 날짜 재생성에서도 무료 한도 안내를 표시한다. 보관된 여행은 원래 날짜와 무관하게 완료 상태로 안내한다. 여행 삭제 확인에는 일정·사진·기록을 복구할 수 없음을 명시한다.
- **이유:** 저장 완료 뒤 경고, 이동시간 복구 불가, 무료 한도 일반 오류, 보관 여행의 여행 중 안내와 불명확한 삭제 경고로 실패한 QA 항목을 해소하기 위해서다.
- **사용자 영향:** 완료한 저장에서 불필요한 이탈 경고를 보지 않고, 실패한 이동시간을 화면에서 다시 조회할 수 있다. 제한·보관·삭제 상태에 맞는 정확한 안내를 받는다.
- **관련 커밋:** 이 변경을 포함한 커밋

### 개발 환경 Plus 무료 업그레이드 허용

- **대상:** 프로필의 Plus 플랜 업그레이드·AWS dev API
- **유형:** 개발 환경 기능 정책 변경
- **변경 내용:** 로컬과 AWS dev 환경에서는 실제 결제 없이 Plus로 전환할 수 있도록 mock billing을 사용한다. Web Function의 `NODE_ENV=production`은 실행 최적화 용도로 유지하고 별도 배포 환경 값으로 dev와 prod를 구분한다. prod에서는 mock billing을 서버 시작 단계에서 거부하고 업그레이드를 비활성화한다.
- **이유:** 실제 기기에서 AWS dev API를 사용하는 통합 테스트에서도 여행·AI 생성 한도와 Plus 전환 이후 동작을 결제 없이 검증하기 위해서다.
- **사용자 영향:** 개발 환경 사용자는 Plus 화면에서 결제 없이 즉시 업그레이드할 수 있다. 운영 사용자의 결제 정책에는 영향이 없다.

### AI 일정 생성을 영속 비동기 작업으로 전환

- **대상:** AI 전체 일정 만들기, 날짜별 일정 업데이트, 생성 로딩·실패 처리
- **유형:** 생성 실행 구조·상태 복구 정책 변경
- **변경 내용:** 생성 요청은 장시간 HTTP 응답을 기다리지 않고 작업 ID와 접수 상태를 즉시 반환한다. 서버는 요청 내용과 대상 날짜, 사용자, 진행 상태를 DB에 저장한 뒤 백그라운드에서 생성하며 모바일은 해당 작업 ID가 완료될 때까지 상태만 조회한다. 앱과 터널 연결이 끊겨도 생성은 계속되고, API가 재시작된 경우에도 다음 상태 조회에서 DB의 미완료 작업을 다시 실행한다. 같은 여행에 실행 중인 작업이 있으면 새 작업을 중복 생성하지 않고 기존 작업을 이어서 확인한다.
- **이유:** 서버 생성은 약 3분 뒤 정상 저장됐지만 최초 HTTP 연결과 앱의 임시 복구 조회가 먼저 종료되어 사용자에게 실패가 표시되는 구조적 문제를 제거하기 위해서다.
- **사용자 영향:** AI 생성 시간이 길거나 화면 전환·일시적인 네트워크 단절·API 재시작이 발생해도 로딩 상태가 실제 서버 작업과 일치한다. 서버가 최종 성공 또는 실패 상태를 기록한 뒤에만 화면이 완료 또는 실패로 전환된다.

- **유형:** 일정 시간 검증·실패 처리 정책 변경

### 장시간 AI 생성 연결 끊김 복구

- **대상:** AI 일정 만들기·날짜별 일정 업데이트 로딩 및 실패 처리
- **유형:** 장시간 요청 복구 정책 변경
- **변경 내용:** 서버가 여행별 최신 AI 생성 상태(`실행 중`, `완료`, `충돌`, `실패`)를 별도 조회할 수 있게 유지한다. 모바일과 터널 사이의 장시간 HTTP 연결이 먼저 끊겨도 즉시 실패 화면을 노출하지 않고, 새 생성 상태를 조회하면서 기존 로딩 화면을 유지한다. 서버 생성이 완료되면 최신 일정을 다시 받아 정상 완료로 전환한다.
- **이유:** 실제 최근 요청은 서버에서 168초 후 HTTP 201로 정상 저장됐지만 Cloudflare 터널이 먼저 `context canceled`로 연결을 종료해 앱만 실패로 판단했다. 생성 품질 문제가 아닌 전송 연결 수명 문제이므로 서버 작업 결과와 HTTP 연결 상태를 분리해야 한다.
- **사용자 영향:** AI 생성이 오래 걸려 네트워크 요청이 중간에 끊겨도 서버 작업이 계속 진행 중이면 실패로 보이지 않으며, 완료된 일정이 자동으로 화면에 반영된다. 실제 서버 생성 실패나 충돌일 때만 실패 안내가 노출된다.
